# PRD 127 — Picker accordion and configurable type order

**Status:** done — 2026-10-06 (closed in the PRD triage). Previously: implemented — 2026-10-05 (phases 1–3 + acceptance round + D8 cleanup built by rapla-impl, browser-checked on the DHBW copy, accepted by the user, committed 1fcccd51a, on dhbw-test since 2026-10-05 02:22); concept 2026-10-04
**Related:** [PRD 123](123-spa-unified-resource-picker.md) (overturns D3 chip wall/"Typ ▾" and D9 *Benutzer* chip), [PRD 119](../119-spa-one-search-resource-picker.md) (overturns D1 ranking in *Alle*), [PRD 120](120-resource-hierarchy-parents-children.md) (nesting stays), [rapla/rapla#598](https://github.com/rapla/rapla/issues/598) (type order not alphabetical since 2.0)

## Abstract

*Alle* is a flat list of tens of thousands of rows (a large deployment) mixing every type with favorites and recents unlabelled on top. The picker becomes one accordion of Favoriten / Zuletzt / Ressourcen / Personen / Benutzer with Swing-style type folders, and the order of the type folders becomes configurable through an `order` annotation on the type (unset: creation order as today; #598 is answered by setting `order`). Mockup: `docs/prototypes/alle-typ-ordner.html` (untracked).

## Implementation

- SPA: `resource/resource-picker.component.ts`, `state/resource-picker.ts` (`rankAll`, `typeChips`, `byLabel`), `state/resource-tree.ts` (`buildTree`, `resourceNode`), `state/resource-selection-store.ts` (chip state → open-section state, `rapla.picker`).
- Type order: new `DynamicTypeAnnotations.KEY_ORDER = "order"`; one comparator in rapla-core used by Swing `TreeFactoryImpl.DynamicTypeComperator`, the admin type tree (`SwingTypeCategoryView`) and the server's type list for the SPA.
- In-type order: the server sorts the lean `resources` list with `SortedClassifiableComparator` (rapla-core, attribute `sorting` annotation, else name); the SPA keeps that order instead of `sort(byLabel)`.
- Rapla 2 on a shared DB keeps unknown type annotations (generic map in `DynamicTypeImpl.setAnnotation`, `RaplaXMLWriter` writes every key) [~/git/rapla2, checked 2026-10-04].

## Goal

- *Alle* without a query shows at most 5 section heads plus one open section; no chips, no "Typ ▾".
- A type with `order` set sorts before every type without; unset types keep creation order; Swing tree and SPA show the same order.

## Scope

### In scope
- Accordion picker (rail and event sheet), search grouped by type, type order annotation (set in the data), server-side in-type sort for the picker, calendar lanes in chip order.

### Out of scope
- Per-user type order; type reorder in the SPA administration (later, PRD 117 territory); any edit UI for `order` — Swing type editor field, drag / menu reorder in the admin type tree (later, super admin only; OQ2/OQ3).

## Open Questions

- **OQ1** — Is the attribute `sorting` annotation used in DHBW/Siegen data? *Resolution (user via rapla-concept, 2026-10-04):* irrelevant — the SPA honours `sorting` everywhere Swing does ("wir haben doch sorting schon … in swing wird es ja auch berücksichtigt"); see D6.
- **OQ5** — Shape of the server-delivered order: the order of the lean `resources` list, or a per-resource sort index? Picker, chip rail and lanes need it; every readable resource is in the lean list, so the SPA can take the position from it. *Resolution (user via rapla-impl, 2026-10-04):* list order — "server sends the list already sorted"; no `sortIndex` field, the SPA drops `sort(byLabel)` and uses the position.
- **OQ7** — Sort every GraphQL resource list the same way (nested `Reservation.resources`, `Appointment.resources`, `AppointmentBlock.resources`), as Swing does for blocks (`RaplaBuilder:195`)? The user raised it ("shouldn't we have a sorting for all resource queries in graphql?"). *Resolution (user, 2026-10-04):* yes — one shared comparator factory, used by `resources` and the three nested fields (Phase 2b).
- **OQ8** — Sort `AppointmentBlock.matchedBy` in tree order too? Then a block matched by several selected resources lands in the lane of the first in tree order (today: first in storage order). *Resolution (user, 2026-10-04):* yes, already implied by D6 "like Swing" — Swing groups by the first selected allocatable in `SortedClassifiableComparator` order ([PRD 100 § lane assignment](../100-spa-block-renderer-unification.md)); `matchedBy` is sorted server-side with `treeOrder()` (Phase 2c), the SPA keeps `matchedBy[0]`.
- **OQ6** — Where do `user` chips sit in the ordered rail — after the resources? (`FilterKind` also names `event`, PRD 078; no code produces such a chip.) *Resolution (user, 2026-10-04):* chips in tree order: resource types, then person types (both by `TYPE_ORDER`, in-type server order), then users A–Z — "Ressourcen vor Personen vor Benutzern" (Swing: *Benutzer* root after the resource and person types).
- **OQ2** — Reorder UI (admin-tree drag, "nach oben / nach unten" menu)? *Resolution (user via rapla-concept, 2026-10-04):* deferred — "das klären wir später, im Moment nur die order annotation".
- **OQ3** — Reorder/edit permission? *Resolution (user via rapla-concept, 2026-10-04):* editing types comes later, super admin only; in this version the annotation lives in the data, no edit UI ("kein edit jetzt").
- **OQ4** — A user who can read only their own account: Benutzer section or a single "meine" row? *Resolution (user via rapla-concept, 2026-10-04):* a single row "Meine Buchungen" / "My bookings" (en + de, PRD 124) replacing the Benutzer section; it selects the own account (`ownerIn`, like today's *meine*, PRD 123 D9). Whoever can read more than their own account gets only the Benutzer section, no extra row ("admins nur benutzer").

## Decisions locked

**D1 — One accordion instead of chips (user, 2026-10-04).** Sections Favoriten, Zuletzt, Ressourcen, Personen, Benutzer; exactly one open at a time ("immer eins wo man gerade ist"); heads without ▸, the open head highlighted and sticky; below the heads type folders, categorization groups and resource nodes keep ▸/▾ and open freely. Start: Favoriten open, Ressourcen when there are none; "⊟ zuklappen" restores that; the open state persists per user. Amended 2026-10-05 (user): at most one open — a click on the open head closes it; heads below the open section stick to the bottom. Nothing opens or closes automatically on selection — not on a click, not for a restored selection after a reload, not for a chip set from outside (user, 2026-10-04, Q1: `pathKeysTo` auto-expansion removed; overturns PRD 119 D12 "open by default"). After a reload only the persisted section is open. Empty Favoriten/Zuletzt are hidden. Overturns PRD 123 D3 (chips + "Typ ▾") and D9 (*Benutzer* chip) and PRD 119 D1 (favorites/recents on top of *Alle*): the chips duplicated what the sections now show. Rejected: freely expandable top level (kept as mockup switch).

**D7 — "+ Neu" type preselect like Swing (user, 2026-10-04).** The type comes from the last clicked picker row, as Swing takes it from the focused tree node (`MenuFactoryImpl.addNewMenus`: a `DynamicType` node → that type, a `Classifiable` → its classification's type): a type folder → that type, a resource → its type, a search type heading → that type (user, 2026-10-05); the last click wins, whether it opened a folder or selected a resource. No clicked row → no preselect. Replaces PRD 122 D3's "from the active type chip".

**D8 — Select-all only where Swing has a node to select; one hit row (user, 2026-10-05).** Swing selects type folders, categorization nodes and resources, never the roots (`CalendarModelImpl` resolves `DynamicType` and allocatables only), so: no "wählen" link on the section heads (Favoriten/Zuletzt/Ressourcen/Personen/Benutzer — the mockup's "pick" link goes); "alle wählen" / "Auswahl aufheben" stays on type folders and categorization groups, the label flipping to "Auswahl aufheben" when every member is selected (today only the big button flipped); for the whole list it exists only while a search is active, as part of the search bar — `Suchfilter „ab" aktiv · 1691 Treffer · alle wählen ×` — and the separate count row below it goes (it duplicated the hit count; without a search the section heads already carry the counts). "⊟ zuklappen" goes too: with D1's amendment a click on the open head closes it, and folders keep their state on purpose. Fix bundled: deselecting checked each item against the chip array (`FilterStore.has` = `some`, O(n²); 5620 chips ≈ 31 M compares, the 2 s "Auswahl aufheben") → one `Set` of chip ids per call.

**D2 — Search is flat, grouped by type (user, 2026-10-04).** A small type heading ("Kurse 6") with the hits indented below, in type-folder order; users last. Each hit is its own row with its parent(s) in small text below (the building relation is otherwise lost); no type label on the right. Nothing opens; expansions made during a search are dropped when the query changes. **Amended 2026-10-05 (user):** the type headings in the hit list are collapsible like type folders (▸/▾, open by default, "Kurs 169" folds away its 169 rows); the fold state is per query and dropped with it. **Amended 2026-10-05 (user, [PRD 119 D13](../119-spa-one-search-resource-picker.md)):** the query comes from the picker's own field above the accordion, not from the top field; the D8 search bar is that field's row.

**D3 — Children keep their own row, like Swing (user, 2026-10-04).** A child is listed under its parent and in its own type folder. Hiding same-folder duplicates was dropped: sub-rooms are their own type, so the case does not arise in practice.

**D4 — Names sort as entered (user, 2026-10-04).** Leading punctuation ("!!!…") is deliberate to reach the top; no special handling.

**D5 — Type order via an `order` annotation (user, 2026-10-04).** Unset by default; types with `order` come first (ascending), the rest keep creation order (`timestampCompare`, user 2026-10-04: "wir lassen die default folge der anlage"); resource types stay before person types. #598 (alphabetical wish) is met by numbering the types. No edit UI in this version — the value is set in the data (XML/DB); editing (type editor field, admin-tree drag renumbering the class) comes later, super admin only (OQ2/OQ3). Rejected: a system preference list (new admin UI in both clients, list drifts from the types), per-user order (no demand), A–Z as the default (changes every existing deployment's order unasked).

*Impact on a shared DB with Rapla 2 (checked 2026-10-04, `~/git/rapla2/rapla` a2450c8d4):* Rapla 2's main Swing tree builds its type folders from `LocalCache.getDynamicTypes()` = `ConcurrentHashMap.values()` (hash order of the type keys), exactly like Rapla 3 before this PRD; only its classifiable model sorts. After Phase 1 Rapla 3 shows creation order (`timestampCompare`: types without a create date go last, then by id), Rapla 2 keeps hash order and ignores `order`. So the two clients differ in type-folder order on the DHBW DB until Rapla 2 is retired; the data is untouched (unknown annotations survive Rapla 2 saves). To be compared on dhbw-test after the deploy.

**D6 — In-type order from the server, like Swing (user via rapla-concept, 2026-10-04).** `SortedClassifiableComparator` (attribute `sorting`, else name) wherever Swing applies it: resource tree (`TreeFactoryImpl`), resource order in the calendar views (`RaplaBuilder:195`), selected resources (`CalendarModelImpl.getSelectedAllocatablesSorted`), HTML calendar pages (`AbstractHTMLCalendarPage:400`). The SPA uses the server order for the picker; favorites and recents keep their own order. **Corrected (user via rapla-concept, 2026-10-04):** the calendar lanes follow the order of the selection chips ("die Reihenfolge der Bahnen bestimmt sich aus der Reihenfolge der chips"), and the chips are ordered like the picker tree, not by click order ("wir klicken ja auch manchmal gruppen an, die reihenfolge der chips an die reihenfolge im baum anpassen"): type order, then in-type server order. Lanes therefore end up in tree order — Swing parity with `getSelectedAllocatablesSorted` after all, plus the type order. Today `filter-store.ts` appends chips in click order and `week-lanes.ts` sorts groups by name — both change (Phase 3). Position of `user` chips: OQ6. Shape of the delivery: OQ5.
