## Abstract

Swing shows conflicts and resource requests in two extra panes; selecting one shows its resource with the conflicting / to-be-approved appointments in normal colour and every other allocation pale. The SPA gets both as accordion sections (PRD 127) and a chip model with two roles — scope and focus — plus two selection contexts, *Planen* and *Prüfen*.

## Implementation

- Swing reference: `TreeFactoryImpl.createConflictModel` / `createResourceRequestModel` (type → resource → entry; conflicts split into enabled / disabled by `checkEnabled`), `ConflictSelectionPresenter.showConflicts` (selection + `setSelectedDate`), `RaplaBuilder:172-189,540-560` (selected conflicts/requests replace the allocatables; `ConflictImpl.getMap` / `ReservationImpl.getRequestMap` decide which blocks stay normal; the rest is drawn as non-filtered).
- Server: a user-scoped list of all conflicts and of all open requests (GraphQL); §12 — a conflict only when both reservations and the resource are readable; tier-3 leak test.
- SPA: `state/filter-store.ts` (chip kinds `conflict`, `request`; two contexts), `views/variable-binder.ts` (scope), `views/week-lanes.ts` / `week-grid` / `month-grid` (pale style; today only `dragsource` has `opacity: 0.35`).

## Scope

### In scope
- Accordion sections Konflikte (n) and Ressourcenanfragen (n), type → resource → entry; disabled conflicts as a sub-group.
- Chip kinds `conflict` and `request`; scope/focus model; Planen/Prüfen contexts; pale rendering.
- Server read queries for all conflicts / all requests of the caller.

### Out of scope
- Approving/rejecting a request from the picker; disabling conflicts from the picker.

## Decisions locked

**D1 — Scope and focus (user, 2026-10-04).** Every chip may contribute scope (what the calendar loads) and focus (what is drawn normally). Resource and user chips: scope (union, PRD 123 D10). Conflict chip: scope = the conflict's resource, focus = the overlapping appointments of both sides. Request chip: scope = the requested resource, focus = the appointments still to be approved. As soon as one focus chip is set, every block outside the focus is drawn pale (Swing's other colour); without focus everything is normal. A click on a conflict/request jumps to its first date.

**D2 — Conflict and request are own chip kinds.** One click makes one chip; its × removes scope and focus together; the label names the case. Rejected: composing them from a resource chip plus event chips (an orphaned focus after removing the resource; an event chip would highlight the whole series, not just the overlapping appointments).

**D3 — Two selection contexts, Planen and Prüfen (user, 2026-10-04).** Favoriten, Zuletzt, Ressourcen, Personen, Benutzer share one selection (Planen). Konflikte and Ressourcenanfragen each have their own (Prüfen). Opening a section shows only the chips of its context; the other contexts' selections rest and are restored unchanged when one of their sections is opened again — in every direction (Planen → Konflikte → Planen restores the resources, back to Konflikte restores the conflict; Konflikte ↔ Ressourcenanfragen likewise; user, 2026-10-04). A click replaces within its own context, Ctrl+click adds. Swing parity: there the resource selection survives while conflicts are selected (`RaplaBuilder:180`). Rejected: accordion as pure navigation (a conflict click would wipe the resource selection), one selection per section (Favoriten vs. Ressourcen would disagree about the same room).

**D7 — Konflikte and Ressourcenanfragen are VIEWS, not picker sections (user, 2026-10-05, rethink after step C).** The view list (top left: Raumauslastung, Übersicht, Termine, Veranstaltungen, Kalender) decides WHAT IS QUERIED; the renderer (Tabelle / Tag / Woche / Monat on the right) decides HOW IT IS DRAWN; the two axes stay independent (PRD 074 / PRD 078). Two new views in the catalog: *Konflikte* (query `conflicts(filter:)` over the selection) and *Ressourcenanfragen* (`resourceRequests(filter:)`). Each view names its selection source for the left pane: the resource picker (Favoriten … Benutzer) for the planning views, the conflict tree (type → resource → entry, disabled as a group) for Konflikte, the request tree for Ressourcenanfragen. Switching the view is the D3 context switch: the Planen chips rest and return with a planning view; Konflikte/Anfragen keep their own chips (D3, OQ4). Every renderer that can take the result draws it — the calendar renderer shows the resource with focus (D1), the table renderer a conflict/request list. **Visibility of open items:** a small red badge next to the view selector, one with the conflict icon and one with the request icon, each with its count — conflicts count only the ACTIVE (not disabled) ones (user, 2026-10-05) —, shown only while the count is > 0; a click opens that view; the list entries *Konflikte* and *Ressourcenanfragen* carry the same icon + count (user, 2026-10-05: "neben dem Dropdown und Konflikte") (replaces the accordion head counts; Swing keeps its conflict list permanently visible). Consequences for step C: the two accordion sections and their `Section` values go; `review-tree`/`review-store`/chips/focus/contexts stay; the left pane switches by view; the hint for an empty Prüfen selection (OQ20) stays in those views. Overturns D3's "opening a section shows only its chips" (now: the view) and OQ7/OQ14/OQ18 as far as they speak of sections. Reason: the view selector had no meaning in Prüfen while a section decided the context; one list for "what is queried" is the existing model. **Default renderer (user, 2026-10-05 02:45):** both review views open in the DAY renderer by default (a conflict is a point in time; the jump lands on that day); the last chosen mode per view sticks afterwards, the default applies only on first open. Bonus (user): as declared views, custom conflict queries become possible like any other view — own filters (`resourceMatching`, `disabledEq`, window) and own table columns via the PRD 074 view mechanism, no new code.

**D4 — Open-request index keyed by resource id (user, 2026-10-04).** Today `FacadeImpl.getResourceRequests` → `queryAppointmentsSync(requestsOnly = true)` scans every appointment of every admin-able resource without a time window (`LocalAbstractCachableOperator:812-889`); the PRD 086 block index does not help (restricted to the plain case, `:834-840`; its gain is the window lookup). The request status already lives per resource id on the reservation (`ReservationImpl.requestStatus: Map<String, RequestStatus>`, `:59`; the enum has only `REQUESTED`). The server keeps `resource id → reservation ids with an open request`, built once at load from those keys and updated incrementally wherever reservations enter or leave the cache (store, delete, multi-pod refresh). Visibility: `canModify(resource, user)` once per resource that has open requests (the check inside `isRequestFor`), then all reservations under the modifiable resources — same result as Swing, cost proportional to the resources with open requests; the type → resource → reservation tree falls out of the keys. `getResourceRequests` (Swing) uses the same index. Section visibility needs no second index: with OQ7 the section shows iff at least one visible open request exists [assumption: a request only arises on a resource with a `REQUEST` permission entry — unverified]. Rejected: a flat set of reservation ids (re-checks every allocation per reservation), block-index flip for `requestsOnly` (no window → no gain), "only from today" (hides past requests Swing shows). Measure the current call on a DHBW data copy (services off) before and after.

**D5 — `conflicts(filter:)` plus a narrow `conflictStats`; tree loaded per resource (user, 2026-10-05).** Same shape as `resources(filter:)` / `reservations(filter:)` and the PRD 079/080 `…Stats` fields:
`conflicts(filter: ConflictFilter): [Conflict!]!` replaces `conflicts(reservationId:)` — `ConflictFilter { reservationIdsIn, resourceIdsIn, resourceMatching: ResourceFilter, from, to (optional — no window by default, like Swing), disabledEq: Boolean (absent = both; `true` = only disabled, `false` = only active — named like `ResourceFilter.isPersonEq`) }`; no filter = every conflict of the caller (OQ5); new field `Conflict.disabled: Boolean!` (Swing `checkEnabled`).
`conflictStats(filter: ConflictFilter, groupBy: [ConflictGroupKey!], aggregate: [ConflictAggregate!]): [BlockStatBucket!]!` — `ConflictGroupKey` is a closed enum `RESOURCE | TYPE | DISABLED` (no `expr`, no key on the other side, so a masked side cannot leak through a bucket); `aggregate` optional, default `COUNT` (only COUNT makes sense). Section head: no `groupBy` / `[DISABLED]`; tree on opening: `[RESOURCE, DISABLED]` (type folders derived in the SPA); a resource's conflicts only when it is expanded: `conflicts(filter: {resourceIdsIn: [r]})`. Reason: the test system has tens of thousands of conflicts for the super admin, a few hundred of them disabled (user, 2026-10-05) — an id list just to count would be ~1.6 MB per start, the full tree several MB and tens of thousands of nodes (estimate, not measured); normal users see far fewer (only modifiable conflicts).
`resourceRequests(filter: ResourceRequestFilter): [ResourceRequest!]!` — `ResourceRequest { resource, reservation, appointments }`, one row per reservation × requested resource (tree leaf and request-chip identity); `ResourceRequestFilter { resourceIdsIn, resourceMatching, reservationIdsIn }`. `resourceRequestStats` (same narrow pattern, keys `RESOURCE | TYPE`) only when request volumes call for it.
Speed comes from inside the server: conflicts from `ConflictFinder`'s in-memory map, requests from the D4 index, permission groups from the PRD 129 cache, every non-scalar field resolved per field only when selected. One rule for every variant: conflicts the caller may modify (Swing), the other side masked when unreadable (`reservation2`/`appointment2` null, `description` "occupied", as `potentialConflicts`). The event sheet moves to `conflicts(filter: {reservationIdsIn: [...]})` and then also sees masked conflicts. No other consumers to migrate: the GraphQL API is pre-alpha, no alias (user, 2026-10-05). Unchecked: whether the PRD 079/080 stats code can serve conflicts or a small own resolver is needed. Rejected: `allConflicts` (second field with other rules), extending only by `reservationIds` (the client does not know which reservations conflict), a `ConflictList { count items }` wrapper (the only object-wrapped list), counting in the SPA from an id list (size above), two fixed fields `conflictCount` + `conflictResources` (same result as one narrow stats field, two special shapes instead of the existing pattern).

**D6 — The other side's ids are not a leak for a party to the conflict; the conflict id is the chip id (user, 2026-10-05).** `Conflict.id` (`CONFLICT;<resource>;<appointment>;<appointment>`, `ConflictImpl.createId`) contains the other side's appointment id. Whoever is a party to the conflict may know that id; Swing already receives it with the full `ConflictImpl` over REST (`RemoteStorageController:463`). Masking applies to the other side's details (names, `reservation2`/`appointment2` objects, description text), not to its ids. The id is deterministic and stable while both appointments exist, so it is the conflict chip's identity and may be persisted (OQ4); a stored id that no longer appears is dropped silently. The schema text "session-scoped … do not persist" on `Conflict.id` is corrected accordingly. An id alone resolves to nothing: `reservation(id:)` returns null when the caller cannot read it (`ReservationGraphQLController:82-100`, `canRead`), the same answer as for an unknown id. So in both `conflicts` and `potentialConflicts` the id fields `reservation2Id` / `appointment2Id` stay filled when the other side is masked; only the objects and the description are masked (`potentialConflicts` changes accordingly — today it nulls the id fields too). Request-chip identity: reservation id + resource id (D5 `ResourceRequest`).
