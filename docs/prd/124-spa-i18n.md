## Abstract

The SPA is hard-wired to German: `LOCALE_ID 'de-DE'`, ~300 literal UI strings (partly
English), and hand-rolled German weekday/month arrays. Swing and the server already ship
nine languages with ~645 keys each (PRD 103). This PRD picks the mechanism that lets the
SPA speak the user's language and reuse that catalogue. End state: switching the user's
language preference renders the SPA (labels, tooltips, errors, dates) in that language
with zero German literals left in `rapla-angular/src/app` outside specs.

### Locale today

- SPA: `{ provide: LOCALE_ID, useValue: 'de-DE' }` + `registerLocaleData(localeDe)` +
  `provideNativeDateAdapter()` (`rapla-angular/src/app/app.config.ts`); no
  `@angular/localize`, no `i18n` attributes.
- Server already exposes the Swing catalogue: `GET /api/locale/{id}?locale=xx`
  (`RemoteLocaleService` / `RemoteLocaleController`) returns `LocalePackage`
  = all registered `I18nBundle`s as `{packageId: {key: text}}` + `I18nLocaleFormats` +
  available languages. Without `?locale` it uses the **user's** `org.rapla.language`
  preference, else the server default. Requires auth (401 anonymous, probed). Base
  bundles total 13 files / ~32 KB.
- Per-user language: `RaplaLocale.LANGUAGE_ENTRY` = `org.rapla.language` on the user's
  preferences (Swing `UserOption`).
- Server language ("Server Sprache"): `AbstractRaplaLocale.LOCALE` = `org.rapla.locale`
  on system preferences (Swing `RaplaStartOption`, `ServerServiceImpl:127`, login page).
- Login page (server-rendered): `?lang` → `raplaLocale` cookie → `org.rapla.locale` →
  `Accept-Language` (`LoginPageController.resolveLocale`).
- Payload: one request returns ALL keys of ALL registered bundles for ONE language;
  missing keys are already filled with the English base value server-side
  (`ResourceBundleList.getBundles` → `bundleManager.getString(…, locale)`).
- Caching (probed): `/api/locale` answers `Cache-Control: no-cache, no-store, max-age=0,
  must-revalidate` (Spring Security default, not overridden in `SecurityConfig`), no
  ETag; `/app/` itself is served `no-store` (`SpaResourceConfig` `setCachePeriod(0)`).
  `/api/auth/me` (`IdentityResponse`) carries no language.

### Server-supplied texts

- Type/attribute/resource/category names on the GraphQL wire (`DynamicType.name`,
  `displayName`, SDL `@displayName`) are resolved against **one server locale captured at
  schema-build time** (`StructuralTypeFetchers.localeFrom`, `ServerLocaleResolver`), not
  per user. The comment there defers per-request locale "IF … real multi-locale demand".
- Reservation warnings (`ReservationChecksController`) are rendered with
  `raplaLocale.getLocale()` — server default, not user language.
- Observation, not in scope to fix here: `ServerLocaleResolver` reads
  `org.rapla.language` from the **system** preferences, while the admin panel writes
  `org.rapla.locale` there; it works only via the `raplaLocale` fallback. See OQ5.

## Options

### A — `@angular/localize`, build-time (one bundle per language)
`i18n` attributes + `$localize`, `ng extract-i18n` → XLIFF, `ng build --localize`
produces `/app/de/`, `/app/en/`, … .
- + Zero runtime cost, compile-time extraction, ICU plurals, Angular-native.
- − 9 builds and 9 served trees; Spring static handler + `/app/` routing must pick the
  tree; language switch = navigate to another base href.
- − Separate catalogue (XLIFF, own IDs): **none of the 645 existing translations are
  reused**, and PRD 103's coverage script/LLM process doesn't apply.
- − Server language preference only reachable via redirect.

### B — Runtime catalogue from the server, Swing keys (own `t()`)
At bootstrap fetch `/api/locale/…` (user preference resolved server-side), keep the
map in a small `I18nService` (signal), templates use a pure `t` pipe, TS uses
`i18n.t('key', args)`. SPA-only strings go into a new server bundle
(`SpaResources.properties` + `_de`… in rapla-core) — same format, same coverage script,
same LLM-translation path as PRD 103. Dates via `Intl` / `LOCALE_ID` set from the same
response before bootstrap.
- + Reuses existing keys (`new`, `delete`, `save`, `cancel`, `appointment`, …) and all
  nine languages on day one; one catalogue for Swing, server, SPA.
- + One build, language switch = reload after saving the preference.
- − No compile-time key check → a tier-5 test asserts every key used exists in the base
  bundle (and a generated key-union type is possible later).
- − Endpoint currently returns **all** bundles (~32 KB base, gzip small); fine, optional
  `?bundles=` filter later.
- − Own plural/format placeholders: Swing uses `MessageFormat` `{0}`; the SPA needs the
  same substitution (a few lines) — ICU plurals don't exist in the properties files.

### C — `@angular/localize` with runtime `loadTranslations()`
`$localize`/`i18n` markup, but translations loaded before bootstrap from a JSON the
server serves.
- + Angular-native markup and extraction, one build.
- − Still its own ID space → needs a key mapping to the properties files or a second
  catalogue; `loadTranslations` must run before any `$localize` evaluation (bootstrap
  ordering), and switching still reloads. Combines A's catalogue cost with B's runtime.

### Recommendation: **B**
Stops at ladder rung 2: the endpoint, the catalogue, the user preference, the fallback
chain and the translation process already exist. A/C would add a second catalogue and
throw away 645×9 translations. Accepted cost: no compile-time key check (covered by a
test) and a small substitution helper.

## Design sketch (B)

1. **Language resolution** (server, unchanged): user `org.rapla.language` → server
   default. The SPA never resolves itself; it takes `language`/`country` from the
   `LocalePackage`. Browser language only matters on the (already localized) login page
   (OQ2).
2. **Bootstrap:** `provideAppInitializer` already awaits `loadIdentity()`; the locale
   fetch runs after it. `LOCALE_ID` must be known before the first component — provide it
   via a factory reading `I18nService.localeId()` and register the nine Angular locale
   data files statically (OQ4).
3. **Strings:** `t` pipe (pure) + `I18nService.t(key, ...args)`; `{0}`-style substitution
   as in `MessageFormat`; missing key → English base value (server already falls back
   per key) → the key itself.
4. **Plurals:** two keys (`appointment` / `appointments`) as Swing does; replaces the
   `'Termin|Termine'` convention.
5. **Dates/numbers:** `Intl.DateTimeFormat(localeId)` / `DatePipe` with the resolved
   locale; the hand-rolled weekday/month arrays go (`Intl` gives `weekday: 'short'`).
   First-day-of-week and 12/24 h follow the locale (Swing: `I18nLocaleFormats`); time
   zone handling is unchanged (LocalDateTime strings).
6. **Material:** subclass `MatPaginatorIntl`/`MatDatepickerIntl` feeding from `t`.
7. **Language switch:** the account dialog gets a language select writing
   `org.rapla.language` (existing preference path), then `location.reload()`.
8. **Server texts:** names stay server-resolved (see OQ3); warnings get the caller's
   locale instead of `raplaLocale.getLocale()`.

## Notes (from the Phase 1/2 reviews)

- `LOCALE_ID` is a `useFactory` singleton, read by Angular after the app initializers — a
  language switch needs a reload; nothing injected during the initializer may read it.
- The `{id}` in `/api/locale/{id}` is not evaluated by `RemoteLocaleController`; the SPA's
  `spa` is an arbitrary placeholder.
- `formatText` deviates from Java `MessageFormat` on a lone `'` (MessageFormat starts a quoted
  run, the SPA keeps it) and prints numbers via `String()` without grouping; no SPA text needs
  either. `RaplaResources_fi.properties` `calendarweek.abbreviation = kv {0,date,w}` would stay
  literal if the SPA ever formatted it with an argument.
- Dynamic keys (`kind === 'PERSON' ? 'resource_new_person' : …`, `shell_mode_*` maps) are
  outside `SpaResourcesKeysTest`'s reach; a typo there shows only as a raw key in the browser.
- For German users `import/`, `account/` and `auth/` dialogs switched from English to German
  (they were English literals before) — worth a line in the changelog.
- PRD 125 § 4 (ETag on `/api/locale`) is PRD 125 Phase 3, not done yet.
