# PRD 066 — GraphQL `reservations(filter:)` Predicate-Driven Allocatable Selection

**Status:** in-progress — Phases 1+2 landed 2026-05-29; Phase 3 (doc migration) partially done. Live-verified against dhbw: 309 reservations in Gebäude B in one round-trip vs prior 2-roundtrip pattern.

**Date:** 2026-05-29

**Siblings:**
- [PRD 055 (done) — Events Read API](done/055-graphql-events-read-api.md) — the `reservations(filter:)` resolver this PRD extends
- [PRD 059 (done) — Typed Where Predicates](done/059-graphql-typed-where-predicates.md) — emits the per-type `whereXxx` shapes this PRD reuses verbatim
- [PRD 028 — Power Search](028-angular-power-search.md) — `searchText` + `matchKind` on the same filter; lands independently

## Goal

Close the gap between the SPA / Swing calendar's primary read pattern and the GraphQL API. Today the calendar query is "show me reservations for the resources I picked in the tree" — and the tree selection composes three pickers:

- **Type selection** — click a type node ("Raum", "Person", ...) → "include all of this type"
- **Per-type filter rules** — narrow within a type ("Räume with Grundfläche ≥ 50")
- **Resource selection** — tick individual entities → "include these specifically, regardless of type or rules"

Today GraphQL forces the SPA into two roundtrips: first `allocatables(filter:)` to resolve ids, then `reservations(filter: { allocatableIdsIn: [...] })`. This PRD collapses that into one round-trip by letting the SPA pass the full tree selection as a single `AllocatableFilter` directly on `ReservationFilter`.

## Scope

In:

- Add `idIn: [ID!]` to `AllocatableFilter` (additive id-selection, union with the type-bucket).
- Add `allocatableMatching: AllocatableFilter` to `ReservationFilter` (reservations using ANY allocatable matching the filter).
- Lock the union semantic between `idIn` and the type-bucket on `AllocatableFilter`.

Out of scope (deferred):

- AND/OR/NOT combinators at the `AllocatableFilter` top level. The current shape (per-type `whereXxx` already carries combinators per PRD 059) covers every real selection — combinators across types are rare and the SPA can fake them with two aliased queries.
- Recursive `AllocatableWhere.where` for "filter X by attributes of an entity X references" — a different shape, deferred (PRD 059 §"Out of scope").
- Where on Reservations themselves (`whereReservation: ReservationWhere`) — same evaluator could apply; separate PRD.

## Locked design

### `AllocatableFilter` — semantic

```graphqls
input AllocatableFilter {
  # Type selection — which DT types contribute to the result.
  typeKeyEq:    String
  typeKeyIn:    [String!]

  # Per-type filter rules — only effective when their type is in
  # typeKeyEq / typeKeyIn (PRD 059, already emitted).
  whereRoom:     roomWhere
  whereLecturer: lecturerWhere
  # ... one whereXxx per resource/person DT, generated by
  # ClassificationSdlGenerator ...

  # Additive id-selection — these ids ALWAYS appear in the result
  # (subject only to §12 canRead). NEW in PRD 066.
  idIn:         [ID!]

  # Cross-cutting refinements — narrow the type-bucket only,
  # untouched by idIn.
  isPersonEq:   Boolean
  nameContains: String
  ownerEq:      ID
  limit:        Int

  # PRD 028 power-search.
  searchText:   String
  matchKind:    MatchKind = SUBSTRING
}
```

**Result formula:**

```
result = (type-bucket: typeKeyIn-matching, narrowed by per-type whereXxx and
          cross-cutting refinements, §12 canRead applied)
       ∪ (idIn-bucket: each id resolved, §12 canRead applied)
```

**Semantic invariants:**

1. **`idIn` always wins over filter narrowing.** An id in `idIn` whose entity doesn't match `typeKeyIn` or any `whereXxx` is still in the result. The user picked it explicitly — filter rules don't apply.
2. **`idIn` does NOT win over §12.** `pc.canRead(entity, caller)` runs on every entity, regardless of whether it came from the type-bucket or `idIn`. Unreadable picks drop silently (PRD 035 §12 — existence not leaked).
3. **`whereXxx` is type-scoped.** `whereRoom: { Grundflaeche: { gte: 50 } }` only filters allocatables whose DT key is `room`; it has no effect on Persons in the same query. (Already PRD 059 behaviour.)
4. **Empty filter** (all fields null) = "everything the caller can read", unchanged from today.
5. **Only `idIn` set** = exactly those ids (with §12), nothing else.
6. **Only `typeKeyIn` set** = all of those types (with §12 + whereXxx), no extras.
7. **Both `typeKeyIn` and `idIn` set** = union per the formula.

### `ReservationFilter` — new field

```graphqls
input ReservationFilter {
  from: LocalDateTime!
  to:   LocalDateTime!

  # Existing scalar narrowers stay.
  typeKeyEq, ownerEq, nameContains, searchText, matchKind, limit

  # Existing — explicit id list (cheap path; skips predicate eval).
  allocatableIdsIn: [ID!]

  # NEW — predicate-driven selection. Reservations using ANY allocatable
  # matching this filter. The SPA sends the full tree selection here
  # (type checkboxes + per-type rules + individual id ticks) in one shot.
  allocatableMatching: AllocatableFilter
}
```

**Semantic:** a reservation is included iff at least one of its allocated allocatables matches `allocatableMatching` (per the `AllocatableFilter` semantic above). If both `allocatableIdsIn` and `allocatableMatching` are set, the result is the union of both id sets.

### Worked example — calendar tree selection

User has clicked the type node "Einrichtungen" with a filter rule "name contains X" and additionally ticked a specific Person:

```graphql
{
  reservations(filter: {
    from: "2026-05-25T00:00:00"
    to:   "2026-06-30T00:00:00"
    allocatableMatching: {
      typeKeyIn: ["Einrichtungen"]
      whereEinrichtungen: { name: { contains: "X" } }
      idIn: ["<person-id>"]
    }
  }) {
    firstDate
    classification {
      typeKey
      ... on LehrveranstaltungClassification { Name Modulcode }
    }
  }
}
```

→ reservations using any X-named Einrichtungen OR the explicitly-picked Person, all §12-filtered.

## Java wiring

- `AllocatableFilter` (the Java record / Map adapter) gains an `idIn: List<String>` field.
- `ClassificationGraphQLController.allocatables(filter:)` evaluator:
  - When `idIn` is non-null, resolve each id via `operator.tryResolve(...)`, drop unresolved or unreadable entries.
  - When the type-bucket is empty (no `typeKeyIn` / `whereXxx` / cross-cutting refinements), iterate the resolved `idIn` set only.
  - When both buckets contribute, union by id (de-dup the rare case where a tree-click picks the same entity by both type bucket and explicit id).
- `ReservationGraphQLController.reservations(filter:)`:
  - When `allocatableMatching` is set, resolve it to an id set up-front (reuses the existing `AllocatableFilter` evaluator).
  - That id set is unioned with `allocatableIdsIn` (existing path) and passed to `queryAppointmentsSync` as `visibleAllocatables`. The post-loop `pc.canRead(r, caller)` continues to gate.

## Plan — 3 phases

1. **Phase 1 — `idIn` on `AllocatableFilter`.** Schema field + adapter + evaluator + tier-3 tests. Standalone usable: `allocatables(filter: { idIn: [...] })` returns the explicit set. Tests: empty `idIn`, non-existent id silently drops, unreadable id silently drops, combination with `typeKeyIn` exercises the union semantic.
2. **Phase 2 — `allocatableMatching` on `ReservationFilter`.** Schema field + resolver wiring that converts the inner `AllocatableFilter` to a resolved id set, then unions with `allocatableIdsIn`. Tier-3 tests: tree-selection equivalent (type + idIn → reservations on union), permission-leak test (non-admin matching predicate that includes hidden allocatables).
3. **Phase 3 — Doc + migration.** Update `dhbwrapla/docs/graphql.md` to use the one-shot pattern; mark the two-step pattern as legacy. Mention the new field in the rapla `docs/graphql.md` query catalog.

## Tests

Tier-3 tests for each phase, using the `testdefault.xml` fixture (Springfield personas — homer / monty / Burns Monty / Simpson Homer, dummy Person DT). Per AGENTS.md §17, examples in tests use these dummy personas only, never real DHBW names.

- **Phase 1**:
  - `allocatablesFilterIdInReturnsExplicitSet` — `idIn: [room-A66-id]` returns just Room A66.
  - `allocatablesFilterIdInUnionsTypeKeyIn` — `typeKeyIn: ["room"]` + `idIn: [lecturer-Y-id]` returns all rooms plus the one lecturer.
  - `allocatablesFilterIdInSilentlyDropsUnreadable` — non-admin querying with `idIn` containing an unreadable id returns the readable subset, byte-identical to the readable-only-ids case (§12 leak guard).
  - `allocatablesFilterIdInIgnoresFilterRulesForExplicitPicks` — `whereRoom: { seats: { gte: 100 } }` + `idIn: [smaller-room-id]` returns big rooms plus the smaller room (filter ignored for `idIn`).
- **Phase 2**:
  - `reservationsAllocatableMatchingResolvesEquivalentToIdsIn` — the same selection expressed two ways returns the same reservation set.
  - `reservationsAllocatableMatchingTreeSelectionMixed` — `typeKeyIn` + `idIn` inside `allocatableMatching` returns reservations on the union.
  - `reservationsAllocatableMatchingPermissionLeak` — non-admin caller with a predicate matching hidden allocatables sees only reservations using readable allocatables; response byte-identical to the all-non-existent case.

## Out of scope

- AND/OR/NOT combinators at `AllocatableFilter` top level. Add when a real consumer needs "predicate-set A OR predicate-set B" in one query; today the SPA fakes it with two aliased calls when needed.
- Recursive `AllocatableWhere.where` (PRD 059 §"Out of scope" defer).
- `whereReservation` typed-where on `ReservationFilter` — same evaluator could apply; separate PRD.
